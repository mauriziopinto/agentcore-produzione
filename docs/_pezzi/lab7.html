Agentic AI Lens: AGENTSEC03 (identità dell'agente, minimo privilegio, autenticazione forte).

Prima di cominciare, se non l'hai già fatto, pubblica il codice comune dei lab da fare da soli con bash ../scripts/prepara_percorso.sh (vedi il Lab 5).

Concetto: un secondo ingresso per i clienti

Il Runtime agent resta quello degli operatori, protetto da IAM. Aggiungiamo un Runtime clienti, protetto da token JWT di Amazon Cognito: AgentCore controlla firma, scadenza e client del token prima di eseguire il nostro codice. Il codice legge dal token chi è l'utente e ne ricava il codice cliente.

Tre cose cambiano rispetto agli operatori: la Memory si separa per utente vero, il CRM riceve sempre il codice cliente dell'utente autenticato, e il cliente non vede lo strumento degli accrediti.

  2. Prepara il codice del Runtime clienti: una copia di quello degli operatori, con un main.py diverso e il controllo dell'identità.

    rsync -a --exclude .venv --exclude __pycache__ app/agent/ app/clienti/
rm -f app/clienti/{approvazione,squadra,remoto,reclamo,sciame,strumenti_aws}.py
cp ../risorse/lab7/main.py ../risorse/lab7/identita.py app/clienti/
    app/clienti/identita.py (estratto)
    class SoloIlProprioCliente(HookProvider):
    def forza_cliente(self, event: BeforeToolCallEvent) -> None:
        if not event.tool_use["name"].startswith("crm___"):
            return
        argomenti = event.tool_use.setdefault("input", {})
        if argomenti.get("id_cliente") != self.id_cliente:
            argomenti["id_cliente"] = self.id_cliente     # il codice dell'utente autenticato

  3. Aggiungi il Runtime al progetto, con l'autorizzazione JWT, e pubblica. Circa 4 minuti.

    source ../.cognito.env
agentcore add runtime --name clienti --language python --authorizer-type CUSTOM_JWT \
  --authorizer-configuration "{\"customJwtAuthorizer\":{\"discoveryUrl\":\"$COGNITO_DISCOVERY_URL\",\"allowedClients\":[\"$COGNITO_CLIENT_ID\"]}}" \
  --request-header-allowlist Authorization
agentcore deploy
    Una trappola che abbiamo trovato La chiave si scrive customJwtAuthorizer, con Jwt in minuscolo. Con customJWTAuthorizer il CLI risponde che manca la configurazione. --request-header-allowlist Authorization serve perché il codice possa leggere il token: senza, l'intestazione non arriva al Runtime.

Due difese, una garanzia

Il prompt dice al modello quale cliente sta servendo, e di solito basta. Ma la garanzia è l'hook: anche se il modello sbagliasse codice cliente, prima della chiamata al CRM il codice lo sostituisce con quello del token. Il prompt guida, il codice garantisce.

In questo lab il Gateway non sa chi è l'utente finale: si fida del Runtime. Per portare l'identità dell'utente fino al Gateway e agli strumenti esistono altre strade, come il Gateway con autorizzazione JWT o il token exchange di AgentCore Identity. Le trovi nella guida all'autorizzazione del Gateway; nel workshop non le abbiamo provate.

La regolaChi è l'utente lo dice un token, non il prompt. Il codice, non il modello, decide di quale cliente si leggono i dati.

Per fissare i concetti

Perché il pool Cognito ha la registrazione autonoma disattivata?

Perché altrimenti chiunque conosca l'ID del client potrebbe crearsi un utente e ottenere un token valido. In un pool per clienti veri la registrazione passa da una procedura controllata, non da un'API aperta.

Chi verifica il token, il nostro codice o AgentCore?

AgentCore, prima di eseguire il codice: firma, scadenza e client consentito. Il nostro codice legge solo lo username da un token già verificato. Per questo può decodificarlo senza ricontrollare la firma.

Cosa succede se Anna scrive nel payload "actorId": "luca"?

Niente: il Runtime clienti ignora quel campo e usa l'utente del token, sia per la Memory sia per il CRM.
